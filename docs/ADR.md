# Архитектурные решения (ADR)

Этот документ фиксирует ключевые архитектурные решения, принятые в ходе разработки ETL-проекта, и их обоснование.

---

## ADR-001: Нормализация схемы БД до 3НФ

**Статус:** Принято  
**Контекст:** Исходные XLSX-файлы содержат денормализованные данные: округа, районы, категории и темы повторяются в каждой строке.  
**Решение:** Разделить данные на справочники (`dim_okrug`, `dim_raion`, `dim_category`, `dim_topic`) и факты (`fact_request`, `fact_response`).  
**Обоснование:**
- Устраняет аномалии обновления (например, переименование округа требует изменения только одной записи в `dim_okrug`, а не тысяч строк в фактах).
- Уменьшает объём хранимых данных (текстовые атрибуты хранятся один раз).
- Упрощает агрегации: `JOIN` по FK быстрее, чем `GROUP BY` по текстовым полям.

**Альтернативы:**
- **Плоская таблица (денормализация):** проще для чтения, но приводит к дублированию и аномалиям. Отвергнута.
- **2НФ (без разделения тем на категории):** темы зависят от категорий, поэтому их нужно выносить в отдельную таблицу. Отвергнута.

## ADR-002: Выбор SQLite вместо PostgreSQL/MySQL

**Статус:** Принято  
**Контекст:** ТЗ допускает любую реляционную СУБД. Объём данных — ~20 тыс. заявок.  
**Решение:** Использовать SQLite (файловая СУБД, встроенная в Python).  
**Обоснование:**
- **Простота развёртывания:** не требует установки сервера, настройки пользователей, портов. Файл `mos_gov.db` можно передать коллеге, и он сразу откроет его в DBeaver.
- **Достаточная производительность:** для 20 тыс. строк SQLite работает быстрее PostgreSQL (нет накладных расходов на сетевой протокол).
- **Соответствие ТЗ:** SQLite явно указан в технологическом стеке.

**Альтернативы:**
- **PostgreSQL:** мощнее, поддерживает партиционирование, но избыточен для данного объёма. См. ADR-007 (масштабирование).
- **MySQL:** аналогично PostgreSQL, но менее удобен для аналитических задач.

## ADR-003: Pydantic V2 для валидации данных

**Статус:** Принято  
**Контекст:** Нужно контролировать качество данных на этапах извлечения и перед загрузкой.  
**Решение:** Использовать Pydantic V2 с кастомными валидаторами (`@field_validator`).  
**Обоснование:**
- **Декларативность:** схемы данных описываются как классы, что делает код читаемым и самодокументируемым.
- **Строгая типизация:** Pydantic автоматически приводит типы (например, `str` → `date`) и отбрасывает невалидные строки.
- **Enum для статусов:** `ResponseStatus` гарантирует, что в БД попадут только допустимые значения (`"Опубликован"`, `"Готовится"`, `"На модерации"`).

**Альтернативы:**
- **Pandas-валидация (через `df.dtypes`):** менее гибкая, не поддерживает сложные бизнес-правила (например, проверку формата даты `ДД.ММ.ГГГГ`).
- **Ручные проверки (`if/else`):** быстро превращаются в спагетти-код. Отвергнуты.

## ADR-004: Переопределение метрики «просрочка»

**Статус:** Принято  
**Контекст:** Исходная формула `overdue = (response_date > sla_date)` давала 0 просроченных заявок, потому что все ответы в датасете пришли раньше SLA (данные за февраль 2019, зимние уборки).  
**Решение:** Расширить определение просрочки: заявка считается нарушившей регламент, если (1) ответ пришёл позже SLA, **ИЛИ** (2) ответа нет, а SLA истёк относительно текущей даты.  
**Обоснование:**
- **Бизнес-смысл:** реальное нарушение регламента — это не только поздний ответ, но и отсутствие ответа в срок. Если заявка опубликована 04.02.2019 с SLA 14.02.2019, и на текущую дату (2026) ответа нет — это явное нарушение.
- **Информативность метрики:** новая формула даёт диапазон 34–100% по округам, что позволяет выявлять проблемные зоны (НАО 100%, ТАО 50%, САО 47%).

**Альтернативы:**
- **Использовать `MAX(response_date)` как контрольную дату:** даёт 0 просрочек, потому что SLA у всех заявок позже этой даты. Отвергнута.
- **Исключить заявки без ответа из расчёта:** искажает метрику, потому что незакрытые заявки — это главная проблема. Отвергнута.

## ADR-005: Нормализация названий округов

**Статус:** Принято  
**Контекст:** В данных встречаются два формата написания округов: аббревиатуры (`"ЦАО"`, `"САО"`) и полные названия (`"Центральный округ"`, `"Северный округ"`). Это приводило к дублированию справочника (21 запись вместо 12).  
**Решение:** Добавить функцию `normalize_okrug()`, которая приводит все варианты к канонической аббревиатуре через словарь `OKRUG_CANONICAL`.  
**Обоснование:**
- **Целостность данных:** один округ = одна запись в `dim_okrug`.
- **Корректность агрегаций:** иначе статистика по «ЦАО» и «Центральный округ» считалась бы раздельно, хотя это одно и то же.

**Альтернативы:**
- **Оставить как есть и объединять в витрине через `CASE`:** работает, но справочник остаётся «мусорным». Отвергнута.
- **Геокодирование адресов и автоматическое определение округа:** избыточно для данной задачи. Отвергнута.

## ADR-006: Идемпотентность через `ON CONFLICT DO UPDATE`

**Статус:** Принято  
**Контекст:** Пайплайн должен быть идемпотентным: повторный запуск не должен создавать дубликаты.  
**Решение:** Использовать SQLite-синтаксис `INSERT ... ON CONFLICT (message_id) DO UPDATE SET ...`.  
**Обоснование:**
- **Простота:** одна SQL-команда вместо `SELECT` + `INSERT/UPDATE` в цикле.
- **Производительность:** SQLite обрабатывает конфликт на уровне движка, без дополнительных запросов.
- **Надёжность:** `message_id` — уникальный бизнес-ключ из источника, поэтому конфликты детектируются точно.

**Альтернативы:**
- **`INSERT OR REPLACE`:** удаляет старую запись и вставляет новую, что ломает FK-связи (если бы они были). Отвергнута.
- **Проверка существования через `SELECT` перед `INSERT`:** требует двух запросов вместо одного, медленнее. Отвергнута.

## ADR-007: Гибридный подход Python + SQL

**Статус:** Принято  
**Контекст:** ТЗ требует использования Python (Pandas, Pydantic) и SQL (SQLite).  
**Решение:** Python отвечает за извлечение, валидацию и трансформацию; SQL — за агрегации и построение витрины.  
**Обоснование:**
- **Разделение ответственности:** Python лучше работает с файлами и бизнес-логикой; SQL оптимизирован для `JOIN` и `GROUP BY`.
- **Производительность:** агрегации на уровне СУБД быстрее, чем `pandas.groupby()` на больших данных.
- **Читаемость:** SQL-запрос для витрины самодокументируем — видно, какие поля и как считаются.

**Альтернативы:**
- **Всё на Python (Pandas):** нарушает принцип разделения ответственности, медленнее на больших данных. Отвергнута.
- **Всё на SQL:** невозможно, потому что Pandas нужен для чтения XLSX, а Pydantic — для валидации. Отвергнута.

## ADR-008: База для расчёта `overdue_rate_pct` — все заявки округа

**Статус:** Принято  
**Контекст:** Нужно определить знаменатель для процента просрочки.  
**Решение:** База = `total_requests` (все заявки округа), а не `answered_requests` (только отвеченные).  
**Обоснование:**
- **Бизнес-смысл:** если округ получил 1000 заявок и ответил на 100, но все 100 с опозданием, то `overdue_rate = 10%` (по базе отвеченных) — это маскирует проблему. Правильно: `overdue_rate = 100%` (по базе всех заявок), потому что 900 заявок вообще не закрыты.
- **Прозрачность:** метрика отражает реальную нагрузку на округ и качество работы.

**Альтернативы:**
- **База = `answered_requests`:** искажает метрику, как описано выше. Отвергнута.
- **База = `requests_with_sla` (только заявки с известным SLA):** логично, но в данных почти у всех заявок есть SLA, поэтому разница несущественна. Отвергнута.
